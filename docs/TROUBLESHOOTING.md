# 排错手册（TROUBLESHOOTING）

全部条目都是**真实踩过的坑**：症状照抄游戏弹出的原文，方便你搜索。每条都给出「原因 → 处置 → 怎么提前发现」。

排错的第一原则：**游戏报错时先读它的 `[対象ファイル]` + `[場所]`**——路径来自 `yst_list.ybn`，行号来自脚本的 `lnos` 表，和 `yuris_text_out\decompiled\…` 的反编译源码**行号一一对应**（证据见 [ENGINE_NOTES.md](ENGINE_NOTES.md) §4）。按行号去看那一条，比盲猜快得多。

## 1. 崩溃：`ラベル … が見つかりませんでした`

```
[対象ファイル] data\script\eris\es_select2.yst
[場所] 970 行目
[内容] ラベル ｣ｴ｣ｵ｣ｴ｣ｵｶｨﾁx が見つかりませんでした。
```

**原因**：`GOSUB` 用**字符串**指定跳转目标（`４５４５定義`），引擎拿这个字符串去 label 表 `ysl.ybn` 里**逐字节比对**。`ysl.ybn` **本作没有发**，所以表里的名字永远是 CP932；如果转码时把这个字面量转成了 GBK，比对就是 `A3B4…` vs `8253…` → 找不到。

那条报错里的乱码就是线索：`A3 B4` 用 CP932 解码正好显示成 `｣ｴ`。

**范围比想象的广**：全游戏审计出 **58 个非 ASCII label 名、115 处引用，全部是坏的**（分布在脚本 36/160/161/176）——这不是一个文件的毛病，是**必然炸**的潜伏 bug。

**处置**：这个问题已在工具里修好了（`transcode_yuris_scripts.py` 的 `collect_label_names()` 把 label 名归入"保持 CP932"家族，实测保留 115 处）。所以：

1. 确认你用的是仓库里的脚本，**没有自己改过** keep 家族；
2. 重跑构建，看校验第 [6] 项是否 `ok`；
3. 如果第 [6] 项 FAIL，说明 pack 里的 label 名被转码了 → 用干净的工具重打包。

**提前发现**：校验第 [6] 项（`the N string(s) naming one of the M non-ASCII label names are still CP932`）。它会解析**全部 227 个原始脚本**（不只是 pack 里的），0.40 s 跑完。

> ⚠️ 别用"字节相等"去判断这类问题：CP932 有**重码**，`'定'.encode('cp932')` 不保证复现文件里的字节（文件里可能是 `92 68`＝`檀`）。判断标准永远是**解码出来的文本**是不是某个 label 名。

## 2. 崩溃：`ルビ記述エラーです。`

```
[エラー] data\script\userscript\10_分岐前前半_文鳴①.txt 32行目 ルビ記述エラーです。
```

**原因**：`《` `／` `》` 在本作里**不是标点，是 ruby（注音）语法字符**。译者把书名写成 `《某奇谈》`，引擎就按注音去解析 → 报错。**而且游戏在这里会直接结束**（`es._mes` 是 OK-only，后面跟 `END[]`，一行最多报一次）。

语法是个**三态状态机**（`eris\es_text.yst` 的 `es.TX.RUBY.CHK`，第 2275 行，每画一行正文前调用一次）：

```
文本 -《- 基字 -／- 读音 -》- 文本
```

| 状态 | 遇到 | 结果 |
| --- | --- | --- |
| 0 | `《` | 开始，状态 → 1（`《` 本身不显示） |
| 0 | `》` | **报错**（没有开过） |
| 1 | `／` | 状态 → 2 |
| 1 | `《` | **报错**（嵌套） |
| 1 | `》` | **报错**（缺 `／`；`《` 紧跟 `／` 也报错＝基字为空） |
| 2 | `》` | 结束（读音为空时**静默**不注册） |
| 2 | `《` | **报错** |
| 结尾 | 状态 ≠ 0 | **报错**（没有闭合） |
| 任意 | 单独的 `《` | **静默从显示里删掉**（丢字，不报错！） |

**处置**（两条都要做）：

1. **书名号用 `〈〉`**（U+3008/U+3009），它们在 CP936 里存在、引擎不认作分隔符。正文里**永远不要**写 `《》`。
2. 注音只写 `《基字／读音》` 这一种形式，且**必须成对**。

**提前发现**：校验第 [7] 项 + 行检器 `ruby_errors()`（`check_glossary.py`，是对 `es.TX.RUBY.CHK` 的忠实移植，**只返回第一条错误**，和引擎行为一致）。另有 `python test_ruby_check.py`（18 个用例）做回归。

> 值得注意：`《` 单独出现时**不报错**，只是把字符从显示里吃掉——这类"明明有字却不显示"的 bug 只能靠 [7] 抓。

## 3. 文字被吞、突然翻页、或停下等你点击

**症状**：某一行中**少了一个字**；或者这一行看着还很长就突然换页；或者画面停住，鼠标不走下一步。

**原因**：这 4 个汉字的 GBK 字节被引擎当**控制码**：

| 字节 | 汉字 | 引擎动作 | 严重度 |
| --- | --- | --- | --- |
| `EF F0` | **镳** | 删除该字 + 写一条空的日志项 | 致命 |
| `EF F1` | **锺** | 未处理，正常显示（但字节对被保留） | 警告 |
| `EF F2` | **矧** | 删除该字 + **强制翻页** | 致命 |
| `EF F3` | **矬** | 删除该字 + **停下等点击** | 致命 |

判定点在 `eris\es_text.yst` 的 `es.TX.CRPREPLACE`（第 991–1075 行）：对每个全角字符，把它的 cp936 字节和 `0xEF` + `0xF0/0xF1/0xF2/0xF3` 逐字节比，命中就 `_strdel` 把字符删掉。`EF` 开头的 GBK 汉字一共 190 个，只有这 4 个能形成**完整字节对**——所以是精确的 4 个，不是"一类"。

**实测受害句子**：`分道扬镳`（含 `镳`）。这 4 个字没有等价写法，**只能整个换掉这个词**。

**处置**：改词。禁用字表：**镳 锺 矧 矬**。

**提前发现**：验收检查第 [8] 项 + 行检器 `control_hits` + 回归测试 `python test_control_check.py`。

> 测这个不要用 `raw.count(b'\xef\xf0')` 直接扫脚本文件——脚本的四个块是异或混淆的，扫出来的全是假阳性。要走 `inj.read_blocks()`。

## 4. 字重怎么调都太粗

**症状**：`--weight regular` 了还是觉得笔画粗；换 `Book` 反而更粗。

**原因**（三条叠加，全是真的）：

1. 引擎**只请求两个 `lfWeight`：400 和 700**，没有第三档；
2. 渲染是 **1 bpp 位图，没有抗锯齿** → 同一字重在屏幕上比带平滑的看起来粗一档；
3. Glow Sans 的 `Book` = **500**，比 `Regular`（400）**更粗**，名字容易骗人。

**处置**：往更细的字重走。最终发布值是 **Light 300，两个槽都用**（400 槽和 700 槽都指向 Light，避免粗体段落突然变粗）。

```powershell
python install_glow_sans.py --weight light --bold-weight light
python install_glow_sans.py --verify
```

再细就只剩动字号了。

**提前发现**：`python preview_glow_weights.py` 生成各字重的对比图，不用进游戏。

## 5. 改了字体或字号，但游戏里没变化

按这个顺序查：

| 检查 | 说明 |
| --- | --- |
| **1. 游戏重启了吗** | 引擎启动时把包读进内存，改完必须重启 |
| **2. 有没有旧的 `save\config.sd`** | ★最常见的坑：玩家在 設定 → フォント一覧 里选过的字体存在这里，**优先级高于** exe 面名表和脚本文面量。改名备份（如 `config.sd.prefont.bak`）后重启 |
| **3. 改的东西需要重新打包吗** | 面名/字号/字距在**包里**→ 必须重新构建；只换字体**文件**（同名）→ 不用重新打包 |
| **4. 包放对地方了吗** | 根目录和 `pac\` **各一份** |
| **5. 字体真的装上了吗** | `python install_glow_sans.py --verify`；脚本字面量那条路径**没有兜底链**，名字对不上会被静默换成 SimSun |
| **6. 字号没变是不是行度量的锅** | 字体行度量不是 1 em 时，`lfHeight` 会被缩放 → 看着"字号调不上去"。见 [ENCODING_AND_FONT.md](ENCODING_AND_FONT.md) §5.1 |

## 6. 打了包但游戏还是日文

| 检查 | 说明 |
| --- | --- |
| 包名是 `update1.ypf` 吗 | 引擎找 `update1.ypf`…`update9.ypf`，**两处都找**：安装根目录 + `pac\` |
| 原版的包也被改了吗 | 不要动原版 `.ypf`；我们的包是"覆盖层"，只含改动过的条目 |
| 是不是改完没重启 | 见 §5 第 1 条 |
| 抽文本时用的是**解包后**的目录吗 | `--indir` 应当指向 `ysbin`（含 `ysc.ybn`/`yst_list.ybn`/`ystNNNNN.ybn`），不是游戏根目录 |
| 文本有没有真的注入 | 构建日志会打印 `N script(s) re-encoded, M unchanged`；全 `unchanged` 说明 `lines.tsv` 的 `new_text` 是空的 |
| 打包工具报过"包构建完成但和游戏里那份不一样"吗 | `build_cn_pack.py` 构建后会回读比较，SHA-256 不一致它会警告复制是否成功 |

## 7. `verify_cn_pack.py` 报 FAIL

八项检查的含义与 FAIL 时的处置：

| # | 检查 | FAIL 说明什么 | 怎么办 |
| --- | --- | --- | --- |
| [1] | `update1.ypf` vs 覆盖层目录条目一致 | 包和构建目录不同步（打包中断/复制错了） | 重新构建，同时构建后不要动 `build\` 里的东西 |
| [2] | 注入的字符串能用代码页 936 解回 | 有字符串不是合法 GBK 字节 | 找到报告里的行：译文里有 GBK 装不下的字符（emoji/异体字），换字 |
| [3] | `WORD` 命令集合与原文一致 | 脚本结构被动过（多了/少了字符串） | 用未被修改的工作包重新注入；不要手改脚本二进制 |
| [4] | 布局块（`cmds`/`lnos`/参数尺寸）未变 | 偏移重排写坏了 | 同上；这是最严重的一类，绝对不能忽略 |
| [5] | OS 对话框要显示的字符串仍是 CP932 | 把走 `MessageBoxA` 的文案转码了 → 显示成 `ｽKﾁﾋｴ_ﾕJ` | 把那个脚本加回"保持 CP932"的家族（`UI_SCRIPTS`/`UI_CMD`） |
| [6] | 命名非 ASCII label 的字符串仍是 CP932 | 见 [§1](#1-崩溃-ラベル-が見つかりませんでした) | 用干净的工具重打包 |
| [7] | 含 ruby 分隔符的对白能解析通过 | 见 [§2](#2-崩溃-ルビ記述エラーです) | `《》` → `〈〉`，注音必须成对 |
| [8] | 绘制文本里没有引擎控制字符 | 见 [§3](#3-文字被吞突然翻页或停下等你点击) | 换掉 镳/锺/矧/矬 |

`[2]` 的坑：注入的字节来自 **Windows CP936 表**，和 Python 的 `gbk` codec 在少数字上**不一致**，所以校验用 `MultiByteToWideChar` 来解，而不是 Python 的解码器。你自己写脚本对比时要注意这一点。

## 8. 一行太长，换行难看

**症状**：一行被折成两行还占了两页；或者文字跑到框外。

**原因**：引擎按像素宽度排版，超宽就**自动分页**（不截断）。当前发布值下一行约 **26 个全角字符**：

```
每字前进量 = 格宽 + 字距 = 30 + (-2) = 28 px
可排版宽度 ≈ 790 - 40 = 750 px  →  750 / 28 ≈ 26 字/行
一屏 5 行
```

**处置**（按代价从小到大）：

1. **改句子**（最省事，推荐）：日文原文很短、中文容易膨胀的地方主动压缩。
2. **调字号/字距**：`python tune_dialogue.py --char-space -4`（更紧）或 `--size "M=28x30"`（更小）。这会**全局**影响所有对白，菜单不受影响。
3. **不要指望引擎帮你缩字**：`lfWidth` 恒为 0，字形不会被压扁。

**提前发现**：行检器有**宽度比警告**（`--width-ratio 1.25`，默认值）。实测 10 195 行译文的字节长比：中位数 0.74×、p95 1.00×、最大 2.50×，**只有 22 行（0.2%）超过 1.25×**。所以这条警告数量不多，值得逐条看。

## 9. 构建提示 "N 个字面量无法重编码"

例如：

```
1 literal(s) could not be re-encoded: yst00042.ybn: '"･･"'  (U+FF65)
```

**原因**：那个字面量里含**CP936 里没有的字符**（这里是半角片假名中点 `･` U+FF65）。它属于"保持 CP932"或"无法映射"的情形，工具**保持原字节不动**（不报错、不丢字）。

**要不要管**：

* 如果它不在 `--report` 里被标成"给玩家看的文本"，**不用管**——保持 CP932 是安全的选择；
* 如果它是**游戏里能看到的字**（例如某个菜单提示），那它显示出来会是日文/乱码，需要**人工改词**（`SUBSTITUTIONS` 只覆盖 4 个已知字符，别的要你自己决定换成什么）。

**做法**：`transcode_yuris_scripts.py --report build\engine_transcode.tsv` 把每个保留的字面量连同原因列出来，逐条判断。

## 10. 移植到别的 YU-RIS 作品

换个游戏，**下面这些常量必须重新推导**（工具里全是可改的参数，不要硬改代码）：

| 常量 | 在本作的值 | 怎么重新得到 |
| --- | --- | --- |
| YSTB 异或密钥 | `0x801DD23F` | 别写死：让 `--key auto` 跑一次（[ENGINE_NOTES.md](ENGINE_NOTES.md) §5），加 `-v` 看分数 |
| exe 的 3 个补丁地址 | `0x442894` / `0x59B0C0` / `0x878008…` | 用 [ENGINE_NOTES.md](ENGINE_NOTES.md) §6 的"找法"逐条定位；换构建后地址一定变 |
| 引擎脚本索引上界 | `181` | 从 `yst_list.ybn` 看：`eris`/`userdefine`/`puserdefine`/`puserdesign` 那段结束的位置（`--max-idx`） |
| 面名槽位大小 | 13 字节 | 看脚本里那个面名字面量的实际长度 → 新名字必须 ≤ 长度-1 |
| 面名原文 | `ＭＳ ゴシック` | 在引擎脚本里搜面名字面量（`FACE_SOURCE`） |
| 文本定义名 | `M` / `NAME` / `M_TATE` | 看 `userdefine\文字定義.txt` 里 `es.TDDEF.SET` 用的名字 |
| 行宽/字距字段 | `@gInt1144(36,19)` / `(36,20)` | 在 `eris\es_text.yst` 里搜字符前进量的加法表达式 |
| 打包用的原包名 | `bn.ypf` | 看 `pac\` 里哪个包含 `ysbin\ystNNNNN.ybn` |
| 游戏 exe 名 | `oujunoshima.exe` | `patch_yuris_charset.py --exe-name <名字>` 或直接 `--exe` 指定 |

**通不过的常见原因**：

* 密钥 auto 找不到 → 脚本量太少或版本不同，手工给 `--key 0x…`；
* exe 补丁地址找不到 → 那是**另一个版本**的 exe，或加壳了；用 `--apply` 前的 dry run 报告看是哪一处找不到；
* 脚本不是 YSTB（magic 不对）→ 不是同代引擎（YSTB 是 v500 一代的格式），本工具链不适用。

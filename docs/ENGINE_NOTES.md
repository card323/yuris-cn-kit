# 引擎逆向笔记（ENGINE_NOTES）

这套工具链背后的事实与取证方法。目的有两个：**让你看得懂工具为什么这么写**，以及**让你换个游戏时能自己重新把同一批事实挖出来**。

本文的对象是实测这部游戏（`oujunoshima.exe`，2 115 584 字节，image base `0x00400000`，CLOCKUP，YU-RIS/E-Ris 系）。逐字节复现用的探针脚本没进本仓库（都是临时文件），但每个结论都写了**怎么重新验证**。

> ⚠️ 工具链里的 `yuris_decompiler`（MIT）是**运行时依赖**，本文只描述格式，不复述它的实现。

## 1. 目录结构：谁是谁

```
安装目录\
  ojunoshima.exe        引擎（PE32 x86，无壳）
  pac\bn.ypf            脚本包（本作的名字；别的作品可能叫 script.ypf 等）
  pac\data.ypf          图片/语音包
  pac\bgm.ypf 等
  update1.ypf …         ★ 引擎优先读这些（根目录和 pac\ 都找），原版不带 → 我们的落点
```

脚本包解包后：

| 文件 | 是什么 |
| --- | --- |
| `ysc.ybn` | **命令/参数名表**。magic `YSCM`，version 2；本作 905 个 ASCII 名字（`COM_*` 指令名 + 参数名）。引擎靠它把字节码里的 `kw_id` 映射成名字。 |
| `yst_list.ybn` | **清单**：`idx → 编译期源路径`（如 `data\script\eris\es_text.yst`、`data\script\userscript\00_プロローグ.txt`）。本作 235 条记录。 |
| `ystNNNNN.ybn` | 脚本本体（YSTB 二进制）。227 个。 |
| `ysl.ybn` | **label 表**。本作**没有**发这个文件（见 §7）。 |
| `ysv.ybn` | 语音等其它资源表。抽文本用不到。 |

`yst_list.ybn` 里的索引把脚本分成两段，这个分界很关键：

| 索引 | 数量 | 是什么 | 我们的处理 |
| --- | --- | --- | --- |
| 0 – 181 | 182 | 引擎脚本：`eris\*`（`es_text.yst`、`es_select2.yst`…）、`userdefine\*`（`メイン定義.txt`、`文字定義.txt`…）、`puserdefine`/`puserdesign` | **整体原位转码** CP932→GBK（`transcode_yuris_scripts.py`） |
| 182 – 234 | 53 | 剧本：`userscript\00_プロローグ.txt` 等（其中 51 个含对白） | 抽出来翻译，按场景注入 |

`DEFAULT_MAX_IDX = 181` 就是这条分界线；两个工具各自负责一侧，互不覆盖。

## 2. YPF v500 容器

```
0x00  'YPF\0'            u32
0x04  version = 500      u32
0x08  entry count        u32
0x0c  header size        u32   (= 32 + 整张条目表)
0x10  16 个 0 字节
0x20  条目表，紧跟数据区
```

每个条目（在表里连续排列）：

```
<IB    murmurhash2(明文名) , 混淆后名字长度
名字字节  （按 NLSwaps 表两两交换做混淆，解码后是 CP932 的 Windows 相对路径）
<BBIIQI  kind, compressed, unpacked_size, stored_size, offset, murmurhash2(存储的字节)
```

要点：

* 名字编码固定 **CP932**，且是引擎**逐字节比对**的资源键（`ysbin\yst00182.ybn` 这种）。所以这个名字**永远不要转码**——工具重建包时用的是原始条目名，没动它。
* 两个哈希都是 **murmurhash2**（引擎里自己实现的），`hash` 算的是**压缩后的存储字节**。我们会重算，`--check` 会验证。
* 每个 blob 后面跟 4 个 0 字节，引擎忽略但我们要照抄，否则和原包长得不一样。
* 原打包器用的是 `YSZLB.DLL`（zlib 1.2.3），逐字节复现不可能——所以 `repack` 只重新压缩**改动过**的条目，其它条目原样搬运。
* 游戏同时存在「根目录」与 `pac\` 两个查找位置，所以**包要放两份**。

## 3. YSTB 脚本格式

```
0x00  '<8I'   magic 'YSTB', version, ncmd, lcmd, larg, lexp, llno, pad
0x20  cmds 块   ——  ncmd 条命令，每条 4 字节
      args 块   ——  larg 字节，每条 12 字节
      expr 块   ——  lexp 字节（所有字符串/常量的共享数据区）
      lnos 块   ——  行号表
```

不变量（我们每次读都断言，读不出来就说明文件不对）：

```
magic == 'YSTB'
ncmd * 4 == lcmd == llno      # 每条命令 4 字节，行号表同长
larg % 12 == 0                # 参数记录定长
pad == 0，且 header 之后不留尾巴
```

四个块在文件里都是**异或混淆**的：按 4 字节一组，与密钥的 4 个字节（大端顺序）异或，末尾不足 4 字节的部分与密钥前几字节异或。脱掉这层就能直接读。

**命令记录**（4 字节）：`code u8`、`n_args u8`、`line_no u16`。

**参数记录**（12 字节）：`kw_id u16`、`type u8`、`assignment u8`、`expr_size u32`、`expr_offset u32`。

* `kw_id` 是 `ysc.ybn` 里的名字序号；**`kw_id == 0` 有特殊含义**：它表示这个字符串不是"给某个参数赋值"，而是一段**裸字符串**——游戏里显示的对白就是它（`type`/`assignment` 同时为 0）。我们的抽文本只认这一种。
* `type` 低 2 位：1=整数 2=浮点 3=字符串；`assignment` 决定是赋值还是比较。
* 版本差异：V200（`es.*` 那批引擎脚本的一部分）命令记录只有字面行号；V300 多一个 `u16 n_para`（`GOSUB`/`RETURN` 的 PINT/RINT 个数）。工具读的是 header 里的 version，两种都吃。

**expr 块是一块"紧凑铺砖"**：每个拥有表达式的参数记录指向一块私有字节区间，这些区间**恰好铺满整块**——无空隙、无重叠、无未被引用的字节。所以：

* 抽文本 = 顺着命令流走一遍、把每条记录的 `[expr_offset, +expr_size)` 切出来；
* 注入 = 把这些切片按偏移顺序重新铺一遍，把新的 `expr_offset`/`expr_size` 写回记录，再改 header 里的 `lexp`。

两种记录**不拥有**数据，要特别处理：三操作数的 `IF`/`ELSE` 和 `LOOP` 会跟一个"半记录"，它的 `expr_offset` 仍然是指向 expr 块的**偏移**（指向分支要跳到的那个表达式），而 `expr_size` 存的是**命令索引**（没有目标时为 0）；`RETURNCODE` 后面那条记录的 `expr_offset` 恒为 0、`expr_size` 就是返回码本身。本作的 13 058 条分支偏移**全部**等于"另一条记录的 `expr_offset`"或正好 `expr_size`——这就是我们能安全重排偏移的依据。

**命令块、行号块、以及分支里的目标命令索引一个字节都不改**，所以行号、label、控制流保持字节一致。变的只有 `expr_size` 和重排过的偏移——这也是"译文可以比原文长"的原因（见 [PIPELINE.md](PIPELINE.md) §2.8）。

## 4. 清单（`yst_list.ybn`）与"报错行号"从哪来

引擎崩溃时弹的那句：

```
[対象ファイル]
data\script\eris\es_select2.yst
[場所]
970 行目
```

* **文件路径**来自 `yst_list.ybn` 的清单记录（不是运行时算出来的）。
* **行号**来自该脚本 YSTB 的 `lnos` 块。
* 这两样和我们的反编译输出**一一对应**：`es_select2.yst` 第 970 行、`10_分岐前前半_文鳴①.txt` 第 32 行，都能在 `yuris_text_out\decompiled\...` 里按同样的行号找到对应语句。

这四个字（`es_select2.yst`、`970`）是**实测**的：改坏了对应字节以后，游戏报的就是这两个数字。所以**遇到游戏报错，先按行号去反编译源码里看那一条**，这是最快的定位方式。

## 5. YSTB 的异或密钥：`0x801DD23F` 是怎么找出来的

密钥是**每部游戏一个**的 4 字节值，写在脚本的加密层里——不知道它就解不出命令流，也就抽不到文本。但它不是密码学意义上的密钥，因为：

1. **密文与明文结构已知**：命令块每 4 字节里的第 1 字节是命令号、第 2 字节是参数个数，参数记录里第 1、2 字节是 `kw_id`。这些字段的**取值范围极小**（命令号 < 命令表长度 905；`kw_id` < 905）。
2. **整块在统计上"明"**：把命令块按 4 字节对齐，`cmd[4i+2]、cmd[4i+3]` 是行号，`arg[12i+1]` 是 `kw_id` 的高字节——在一大堆脚本里，**这些位置上出现最多的那组字节，就离真实密钥不远**。

所以 `extract_yuris_text.py::recover_key()` 做的是：

```
1. 统计所有脚本在若干"高字节位置"上的字节众数 → 候选密钥字节（4 个）
2. 把最可能的那 1–2 个字节暴力展开，用 "命令号必须 < 命令表长度" 剪枝
3. 每个候选都拿真解析器验一遍（能否走完整个命令流、参数条数是否自洽）
4. 全过的那个就是密钥
```

工具默认 `--key auto`：先试上游两个已知值（`KEY_200 = 0x07B4024A`、`KEY_300 = 0xD36FAC96`——作者另一部作品用的），都不行才走恢复。本作实测密钥是 **`0x801DD23F`**。

`--key 0x801DD23F` 可以跳过恢复（更快），但换游戏时**先让 auto 跑一次**——它会把分数打出来（加 `-v`），你能看到证据。

> 这一层"混淆"只能挡住"随便打开文件看一眼"，挡不住统计。所以"不知道密钥就抽不出文本"是对的，但"密钥有多难得到"取决于脚本量——这种规模的脚本集，几秒钟就够。

## 6. exe 里 5 处写死的 CP932 假设（也是我们要打的补丁）

引擎**没有任何"代码页"配置项**：它把 Shift-JIS 的字节规则直接编进了机器码。要显示 GBK，必须在这 5 处动手，其中 3 处是 `patch_yuris_charset.py` 改的。

### 6.1 前导字节表（`VA_LEN_TABLE = 0x59B0C0`）★补丁点

引擎自己算"这个字符占几个字节"用一张 256 字节的表：

```
nCount = lenTable[str[0]] + 1        # 0x442360 / 0x442366 处附近
```

原版放的是 **SJIS 的前导字节**（0x81–0xFC，去掉 0xA0/0xC7/0xC8）；CP936 要的是 **0x81–0xFE**。不改这张表，GBK 里 0xFA–0xFE 开头的汉字会被算成单字节，字符串切分会错位——后果是**文本显示截断/后续乱码**。

**找法**：在 exe 里找一段 256 字节、只在 0x81–0xFC 区间非零、形如 `01 01 01 … 02 02 …`（首字节 1、紧跟 0）的表；或者反查上面那个 `lenTable[..] + 1` 的指令模式（本作约 55 处引用）。

### 6.2 `lfCharSet`（`VA_CHARSET = 0x442894`）★补丁点

引擎构造 `LOGFONTA`（构造函数 0x4426C0）时**从来不写 `lfCharSet`**，字段留在 0，也就是 `ANSI_CHARSET`；GDI 于是用**进程代码页**（日文机器上是 932）去解码传进来的 ANSI 字符串 → GBK 字节被当 SJIS 解 → 半角片假名乱码。

原版那 7 个字节是：

```
C7 43 04 00 00 00 00     mov dword ptr [ebx+4],0    ; lfWidth = 0
```

补丁替换成（**不改变文件长度**）：

```
C6 43 17 86 90 90 90     mov byte ptr [ebx+0x17],0x86 ; GB2312_CHARSET
```

被顶掉的 `lfWidth = 0` 是空操作：`LOGFONTA` 数组在 `.data` 末尾的零初始化 BSS 区，没有任何代码写过 `lfWidth`。写进 0x86 以后 GDI 就会按**代码页 936** 解码。

**找法**：搜 `C7 43 04 00 00 00 00`（`lfWidth` 归零），确认它前面是 `LOGFONTA` 的填充代码、后面跟着 `CreateFontA`/`CreateFontIndirectA`。

### 6.3 默认字体表（`VA_FONT_SLOTS = 0x878008/0x878018/0x878028`）★补丁点

`.rdata` 里有一张**面名表**，引擎启动时用 `EnumFontFamiliesExA`（构造器 0x403AF8 附近的循环，0x403B84 处取表项）把系统装了的字体列出来，然后为它的 8 个字体槽各挑**第一个"系统里真的存在"的名字**（三个相邻 immediate 压栈：`0x403B8B` / `0x403B9C` / `0x403BAA`）。

* 每个槽 **16 字节**，所以替换后的 `名字 + NUL` 必须 ≤ 16 字节（工具会强制检查）。
* 因为**第一个存在的就赢**，槽 0 才是真正的选择，槽 1/2 只是兜底。
* 名字走的是 `CreateFontA`，即用**进程 ANSI 代码页（932）**解码，所以必须写字体注册的 **ASCII 名**（`SimSun`、`MS Gothic`），别写本地化名。
* 这张表是引擎的**默认面**：脚本没显式指定的部分（菜单、设置、消息窗等）用它。对白/选项/N 名牌是脚本通过 `FONT[NAME=…]` / `TD.FONT.SET` 指定的 —— 这正是我们改字体时要动**脚本文面量**（`transcode_yuris_scripts.py --face`）的原因。

`--fonts` 三个可选值：`--fonts shipped`（还原原版日文字体）、`--fonts "Microsoft YaHei,SimHei,SimSun"`（推荐，缺字兜底链）。

**找法**：在 `_RDATA` 里找成组的短字符串（长度都 < 16），其地址被三个相邻 immediate 压栈，附近有 `EnumFontFamiliesExA` 的 IAT 引用。

### 6.4 `EF F0–F3` 这 4 个控制字符（**不是补丁点，是知识**）

引擎在 `es.TX.CRPREPLACE`（`eris\es_text.yst` 第 991–1075 行附近）里，把**特定字节对**当成控制码：

| 字节 | 日常字 | 引擎动作 |
| --- | --- | --- |
| `EF F0` | 镳 | 吞掉（swallow） |
| `EF F1` | 锺 | 保留/空操作 |
| `EF F2` | 矧 | 强制分页 |
| `EF F3` | 矬 | 停下等点击 |

这 4 个字在 GBK 里刚好整体落在 `EF F0`–`EF F3`，于是**汉字变成了控制码**。190 个 GBK 汉字以 `EF` 开头，其中只有这 4 个是"完整的字节对"，所以只有这 4 个不能用。工具链把这条编成了 linter 规则（`check_glossary.py` 的 `control_hits`）+ 校验第 8 项 + 回归测试 `test_control_check.py`。

**找法**：看 `es_text.yst` 里那串 `es.TX.CRPREPLACE` 的字节比较；或直接构造含 `EF F0`–`EF F3` 的文本，观察渲染行为。

### 6.5 逐字节比对的 label 名 / 资源名（**不是补丁点，是知识**）

`GOSUB` 用**字符串**指名目标，引擎拿这个字符串去 label 表/资源表里**逐字节比对**。这些名字（`４５４５定義`、`CM_QUAK_左1`、`BGM_全消去`、`tip/…`、`cgsys/…`）因此必须保持 CP932——改了字节就"找不到"。详见 §7。

## 7. 为什么有些字面量必须留在 CP932

我们的目标是把文本变成中文，但有四类字面量**保持原样**（`transcode_yuris_scripts.py` 的四个 keep 家族）：

| 家族 | 例子 | 为什么不能转 |
| --- | --- | --- |
| 资源名 | `tip/文鳴_コート_通常_右`、`cgsys/extra/cgmode/num_ページ数/num_`、`00_プロローグ.txt`、`C:\...exe` | 引擎拿它**逐字节**和归档索引/脚本表比对，转码就找不到图/语音/脚本 |
| label 名 | `４５４５定義`、`CM_QUAK_左1`、`BGM_全消去` | label 表 `ysl.ybn` **本作没发**，表里的名字仍是 CP932，转码后比对必然失败（实测：章节选择崩溃，报 `ラベル ｣ｴ｣ｵ｣ｴ｣ｵｶｨﾁx が 見つかりませんでした`） |
| OS 对话框要显示的 | `"終了確認"`、`"アプリケーションを終了します。宜しいですか？"` | 这些走 **ANSI Win32 API**（`MessageBoxA`/`DialogBoxParamA`/`SetWindowTextA`），用**进程代码页**（系统 932）解码，跟字体里的 0x86 无关；转成 GBK 反而显示成 `ｽKﾁﾋｴ_ﾕJ` |
| 剧本也用的字面量 | `なし`、某个 shake 模式名 | 剧本把同样的字符串传给引擎例程做比较，剧本侧保持 CP932（注入只改对白），引擎侧也必须保持 |

`ysl.ybn` 没发这件事有个很实际的推论：**我们没法翻译 label 名，也不需要**——它只是内部标识，玩家看不到。但它必须留在 CP932，这就是校验第 6 项存在的理由。

判断"资源名"的规则故意**过宽**（带 `/`、`\`、或资源扩展名就保留）：丢一张图比多留一句日文严重得多。被误伤的纯文本（`■BGM/SE VOL+`、引擎自己的报错提示）在 `DISPLAY_CP932` 里单独列出来重新转码。

## 8. 引擎**没有**完整性校验（所以"绕过校验"这件事不存在）

这条值得单独说，因为很多人会问"你要不要绕过校验"。逐项证据（本作 exe）：

| 找什么 | 结果 |
| --- | --- |
| `Crypt*` / `BCrypt*` / `WinTrust*` / `CertVerify*` 导入 | **没有** |
| SHA-256 / SHA-1 / MD5 常量或算法特征 | **没有** |
| 对 `.ypf` 全文的哈希比对 | **没有**；`hash` 字段是 murmurhash2，只校验**单个条目**的存储字节 |
| 对 exe 自身签名/尺寸的检查 | **没有**（改完 exe 照跑，实测） |
| 对脚本数量的检查 | **没有**（我们只打包**改动过**的 97 个条目，游戏从两个位置合并读取，一切正常） |

那么项目里出现的 `SHA-256` 是什么？**是我们自己的文件身份对照**：`build_cn_pack.py`/`tune_dialogue.py` 用它判断"刚构建出来的包"和"游戏目录里正在用的包"是不是同一个文件，只决定要不要复制。跟游戏无关。

这一条对发布很关键：**没有校验要绕，也不需要给用户打任何"绕过补丁"**——exe 补丁只是为了让它按代码页 936 解码，不是破解授权。

## 9. 已经审计过、确认安全的字符路径

改完引擎、注入完文本以后，我们对"所有会被引擎解析的字符串"做过全量审计（`audit_char_syntax.py`、`audit_engine_literals.py`），结论：

| 路径 | 状态 |
| --- | --- |
| 对白 `WORD` 字符串 | 安全：只做等价的偏移重排，命令块/行号块不变 |
